## 1. 产品目标与已确认要求

建立一个统一学术工作入口，使用户通过自然语言描述需求，得到适合其材料、研究类型和目标的工作方案；用户也能独立使用某个专业技能。

系统以经用户确认的 Markdown 论文为核心内容源，通过可组合组件建立版本化模板，由代码强制模板生效。写作与科学审查由当前 Codex 完成；测试、格式转换、编译、渲染和程序验收全部在 GitHub Actions 完成。

### 1.1 已确认的产品要求

| 编号 | 要求 | 实现约束 |
|---|---|---|
| R01 | 一个总技能接收需求、规划并衔接专业技能 | 同一会话按需加载技能，首版不增加独立大模型服务或自动多代理 |
| R02 | 提供独立的技能说明与使用指导 | 每个技能有用途、输入、输出、调用示例、前置条件及边界 |
| R03 | MD 论文先定稿 | 题目、摘要、章节含义、顺序、逻辑、公式、图表和文献先在 MD 确认 |
| R04 | 写 MD 前询问是否有用户模板或参考论文 | 已提供的材料直接使用；没有时推荐已登记模板供确认 |
| R05 | 模型先凝练、验证和确认 | 设计方向获批不能代替数学验证；已有论文的纯格式处理单独标记验证范围 |
| R06 | 先询问中文和英文字体 | 提供适用选项，接受自定义字体；不能静默替换 |
| R07 | MD 确认后获得生成 Word 的授权 | 有明确且仍有效的生成指令时复用，不重复询问 |
| R08 | 每个图表有名称、按顺序编号并与正文引用对应 | 当前用户约定为图题在上、表题在下 |
| R09 | 版式由代码与固定母版强制执行 | 内容不能输入字号、页边距、栏数、分节、样式或模板路径 |
| R10 | 模板组件能共享和组合 | 共用功能复用实现；特殊功能通过有契约的扩展组件加入 |
| R11 | 首次生成版本保留 | 失败产物作为诊断版交付，不能以修订版替换并称为首版 |
| R12 | 生成后提供视觉附件和复检报告 | 按清单逐页复检，记录运行 ID、产物指纹、页码和问题对象 |
| R13 | 用户批准后再修复 | 修复授权绑定指定问题项或明确范围；每轮重新验收并提交报告 |
| R14 | 所有执行性验证在 Actions | 本地只编辑、阅读、提交、查询、下载与查看云端预览 |
| R15 | 优先使用成熟开源方案 | 保留来源与许可证；优先依赖调用，其次按明确授权改造源码 |
| R16 | 首批建设已批准的 9 类模板 | 完整清单见第 7 节；不擅自扩充为其他期刊 |

### 1.2 规则适用范围

1. 当前个人偏好不自动成为其他用户的通用规则。图题在上、表题在下作为本项目明确用户选择记录。
2. 对目标期刊或比赛，先呈现官方要求与用户偏好的冲突。用户可以选择官方提交版或个人审阅版；冲突未解决前不自动宣称符合官方要求。
3. 已有 `reference-journal-v1` 的正文双栏、不跨栏规则继续用于该模板。新模板的正文栏数由其已确认规则决定，不将双栏硬套到国赛、研赛等全部场景。
4. 已发表参考论文优先用于提炼实际表达与版式；参考之间不统一时使用对应目标的官方材料消歧。《系统工程与电子技术》官方模板仅在该目标或用户指定的原参考方案中使用，不作为美赛、IEEE 等其他目标的通用消歧依据。
5. 论文事实、数据和数学判断不能由模板推导。官方强制的匿名、提交材料等要求与写作风格分开记录。

### 1.3 本轮不包含的工作

不创建或安装新技能，不变更正式生成器，不发布论文或投稿，不产生新的测试论文、DOCX 或 PDF，不执行本地验证，也不重新引入此前删除的复杂论文和临时校验目录。

## 2. 既有工程审查与迁移起点

本节结论来自对工作区源码的静态阅读，不代表新一次测试结果。

| 对象 | 当前实际状态 | 迁移处理 |
|---|---|---|
| 本机已安装技能 | 仍是旧版说明与脚本 | 新套件验收前保持原安装状态；不把候选源码直接覆盖安装目录 |
| 仓库候选实现 | `0.2.0-rc1`，具有固定母版与内容填充链路 | 作为迁移基础，保留有效转换和保留检查 |
| 模板资产 | `reference-journal-v1`，只有 `front/end` 两个母版变体 | 保留兼容入口，新增模板注册表 |
| 模板定位 | `locked_template.py` 将 POLICY 固定为一个 JSON 路径 | 改为按模板 ID、版本、变体解析注册资产 |
| 页面与栏宽 | A4、2.2 cm、正文双栏；部分参数直接写在函数中 | 抽为页面组件与区域计划，按资产契约检查 |
| 样式与字体 | 开源固定字体和若干固定字号 | 改为经用户确认的字体包与样式集；生成请求仍不能直接覆盖 |
| 内容共同表示 | Pandoc AST、原生 OMML、共同引用映射 | 保留并扩展角色、区域和对象映射 |
| 题注 | 当前程序仍偏向表上题、图下题 | 参数化位置，迁移本项目偏好为图上题、表下题 |
| 模型检查 | 有模型报告及源文件指纹绑定；部分实验判断依赖中文标题正则 | 保留证据绑定，改为章节角色、事实和结果对象检查 |
| 验收报告 | 构建、自动验收、视觉审阅已经分开记录 | 增加视觉“已完成但发现问题”和用户交付审批状态 |
| Actions | 已有技能 CI、文档任务、独立 Word 对比实验工作流 | 保留正式工作流；对比实验继续隔离 |
| 用户审批 | 还没有覆盖 MD、字体、生成和逐项修复的完整状态模型 | 新增审批事件与有效性检查 |
| 打包 | 排除私人材料，但当前是单技能打包 | 扩展为多技能套件与一个共用内核，检查安装包不泄漏项目材料 |

需要改造的主要文件：`scripts/studio/locked_template.py`、`pipeline.py`、`manuscript.py`、`latex_layout.py`、`qa.py`、`visual_review.py`、`ci/package.py` 和两个正式 Actions 工作流。旧 `docx_layout.py` 的自动通栏实现不能重新进入正式链路。

### 3.2 推荐技术栈

```text
技能说明与规划：Codex 原生 Agent Skills + 按需加载 references
写作与审查：K-Dense 定向改造 + 当前模型专用规则
模板契约：YAML/JSON + JSON Schema + jsonschema
MD片段组合：Jinja2 + Pandoc Markdown
内容共同表示：Pandoc AST + 既有稳定对象映射
Word：版本化母版 + docxtpl变量填充 + python-docx + lxml/OOXML
公式：Pandoc原生OMML + 既有可逆排版适配
LaTeX：Pandoc + 登记模板 + 共用区域、编号和语义对象
文献：Pandoc citeproc + CSL + 已核实BibTeX/CSL JSON
流程状态：transitions + JSON事件记录 + Git版本
云端：GitHub Actions + XeLaTeX + LibreOffice + Poppler
验收：复用既有内容/版面检查 + 针对新增契约补充检查
```

这是在现有技术方案上增加成熟的变量填充、模板和状态管理依赖，不另起一套 Word 排版引擎。

### 3.3 已检查的关键源码与适配点

| 来源 | 阅读对象 | 可复用能力 | 必须适配的地方 |
|---|---|---|---|
| K-Dense scientific-writing | SKILL、`audit_claims.py`、`check_consistency.py` 的关键实现 | 主张与证据登记、数字和方法结果一致性 | 上游按物理行识别部分主张；中文 MD 自动换行、公式和表格需要 AST 适配；不能把全部数字误作实验数据 |
| K-Dense peer-review | SKILL、`validate_claim_evidence.py` 的关键实现与资产目录 | 有证据边界的检查清单和审查输出 | 用于作者自审；保留授权边界，复用已给授权，不照搬成重复询问的期刊审稿流程 |
| K-Dense venue-templates | SKILL、`query_template.py`、模板资产目录 | 目标、版本与官方来源登记 | 上游只有部分具体期刊骨架，不能将其示例当成本文 9 类模板；需核对独立资产许可证 |
| K-Dense citation-management | SKILL、`doi_to_bibtex.py` 及脚本目录 | DOI 和文献元数据获取、格式化与核对 | 仅查询必要公开标识；数学研究优先出版社、Crossref、arXiv，不强制医学数据库或额外付费服务 |
| docxtpl | `template.py` 的 render、页眉页脚、变量转义相关代码 | 在固定母版中替换变量，保留母版样式 | 明确启用转义；拒绝控制字符和任意 RichText 字体；不通过 subdoc 导入未经净化的输入样式 |
| docxcompose | Composer 的插入、样式、分节与页眉处理 | 有现成 DOCX 关系和资源合并处理 | 主文档页眉页脚优先，后续文档页眉忽略；不能作为自由拼接不同论文母版的保证 |
| transitions | `core.py` 的条件、Transition 和 Machine | 条件化状态迁移 | `auto_transitions=False`；用户批准事件不能由运行成功事件代替 |
| 现有工程 | 母版、AST、数学排版、回读、页面检查与 Actions | 已经具备转换和失败诊断链路 | 移除仅适用一个模板的硬编码，改造编号对齐和题注规则 |

相关能力由[docxtpl 文档](https://docxtpl.readthedocs.io/en/latest/)、[python-docx 样式说明](https://python-docx.readthedocs.io/en/latest/user/styles-understanding.html)、[Pandoc 官方手册](https://pandoc.org/MANUAL.html)支持。docxtpl 支持母版变量，不提供数学正确性判断；Pandoc 输出可编辑 OMML，不保证任何表达式自动适合任意栏宽。

### 3.4 暂不采用的整体方案

| 方案 | 本轮决定与理由 |
|---|---|
| LangGraph、CrewAI 或另建 Agent 服务 | 原生技能按需组织已能覆盖当前流程；首版不增加第二个模型运行器、密钥和自动代理调度 |
| 全面迁移 Quarto | 支持 Markdown 多输出，但仍需要固定母版契约与特定 Word 分节适配；当前加入会重复既有转换链路。参考其[Word 样式和扩展机制](https://quarto.org/docs/output-formats/ms-word-templates.html) |
| 任意 DOCX 子文档合并 | 拼接可能影响样式、分节和页眉；先组合规则再构建母版。[docxcompose 明确说明页眉页脚处理方式](https://github.com/4teamwork/docxcompose#headers-and-footers) |
| 新的 LaTeX → OMML 引擎 | 保留 Pandoc 已有引擎；转换失败报告具体表达式，先定位上游支持情况 |
| 直接整体安装上游科学技能包 | 会带入大量无关技能、服务和本地执行流程；只改造需要的模块 |
| 首版直接启用 pandoc-crossref | 属于成熟候选，但与既有编号映射重复，且要求匹配 Pandoc 构建版本；先保持一个编号权威源。新增章节编号需求时再做 Actions 适配评估。[项目说明](https://github.com/lierdakil/pandoc-crossref) |
| 付费 Word 渲染或模板 API | 不列为依赖；使用免费开源链路，清楚标识 LibreOffice 兼容校样 |

### 3.5 需要新增的最小业务代码

本次检索没有发现可直接满足本项目全部规则、9 类中文/英文模板、审批绑定和双输出验收的单一开源成品。需要新增的部分限定为：模板与组件注册适配、区域计划解析、审批和指纹关联、结果对象证据适配、统一检查报告及修复范围校验。

不新增 Markdown 解析器、模板表达式语言、DOCX ZIP 底层引擎、公式转换器、PDF 渲染器、通用状态机框架或文献排版引擎。

### 4.1 技能组织原则

采用“1 个总技能 + 1 个说明技能 + 8 个专业技能”，共 10 个可独立识别的技能入口。总技能不把其他技能全文塞进自身 SKILL；通过能力目录选择需要的技能，读取对应说明，再在当前会话继续。

专业技能保持独立输入与输出；既有授权和有效阶段产物可以复用。每个入口的名称与描述要区分完整项目规划、写作、只审查、只导出和只检查等需求。[官方技能规范采用按需披露机制](https://learn.chatgpt.com/docs/build-skills)。

这里的“调用技能”是当前 Codex 加载并遵循技能说明，不承诺宿主提供未存在的技能 RPC，也不自动创建其他会话或启动子代理。

### 4.2 共享内核与分发

首版在现有私有仓库内维护多技能和一个 `studio` 内核，Actions 使用仓库内核执行。个人安装包包含 10 个技能目录及必要的传输入口；转换依赖只安装在 Actions runner。

说明与规则通过打包清单共享；不能让每个专业技能安装不同版本的转换程序。每个技能记录 `suite_version` 和 `required_capabilities`，任务运行核对云端引擎版本。

OpenAI 现行文档建议多技能分发使用插件；本项目先交付经验证的个人技能套件，预留[官方插件打包适配](https://developers.openai.com/plugins/build/plugins)。本轮不创建插件、不变更插件缓存，也不依赖模板图库专用技能。普通 MD 模板包不冒充宿主的 Artifact Template。

## 5. 技能职责、输入输出和独立调用

| 技能 ID | 用户名称 | 输入 | 输出 | 边界 |
|---|---|---|---|---|
| `reference-paper-studio` | 学术论文总技能 | 自然语言、已有材料、已有进度 | 工作方案、选择、进度、任务衔接 | 统一审批与交付；不重复执行已有有效阶段 |
| `paper-studio-help` | 技能说明与使用指导 | 用户想做的事或技能名称 | 使用说明、材料清单、调用示例 | 只解释时不创建论文、跑 Actions 或修改文档 |
| `paper-reference-research` | 参考论文与规则研究 | 参考论文、目标、年份/文章类型 | 来源档案、结构规则、版式证据、冲突清单 | 不把扫描件或低质量抽取视为可靠精确版式证据 |
| `paper-model-review` | 模型凝练与验证 | 题目、模型、代码、数据、现有验证 | 正规数学模型稿、审查与验证报告 | 区分定义完整、理论审查、求解成功、复现实验及作者确认 |
| `paper-md-write` | MD论文写作 | 已确认模板、模型与事实材料 | 统一 MD 初稿、旁置证据登记 | 不生成无证据结果；不自动进入 Word 导出 |
| `paper-md-review` | MD论文审查 | MD、图表、文献、证据 | 审查报告、待确认项 | 只审查不修改；用户明确授权改写时再衔接修复 |
| `paper-template-compose` | 模板组合与冻结 | 目标模板、用户模板、已确认选择 | 组合计划、登记母版、契约与清单 | 发布过的母版不可由单次稿件改写；新组合属于受控模板构建 |
| `paper-export` | 文档生成与云端验收 | MD 快照、登记母版、字体选择、有效授权 | 首版 DOCX、LaTeX、双 PDF、PNG、自动报告 | 生成不等于验收通过；不自动修复失败 |
| `paper-visual-review` | 视觉复检 | 云端校样或用户指定 Word | 逐页附件、复检报告、问题清单 | 输入 Word 需要云端转换才能查看页面；复检本身不修正文档 |
| `paper-revise` | 论文修复与迭代 | 已批准问题项、对应版本、修改范围 | 修订版、差异、重验收和新报告 | 不超出批准范围；科学内容变化回到 MD 审批 |

### 5.1 说明技能的固定说明卡

每个技能的说明卡包含：名称、适用问题、需要材料、交付物、允许独立调用的条件、哪些动作需要批准、可复用哪些旧产物、运行位置、调用示例和当前能力限制。

能力目录以 `skill-catalog.yaml` 为源，说明技能与总技能共用；构建说明文档时从该目录生成，避免两套描述失配。新增技能必须同时登记说明卡和路由测试场景。

示例调用：

```text
$reference-paper-studio 我有比赛模型和代码，希望整理成期刊论文，先规划。
$paper-studio-help 我只想检查Word，不想修改，应该使用哪个技能？
$paper-reference-research 只分析这两篇参考论文的结构和规则。
$paper-model-review 只凝练与验证数学模型，先不要写论文。
$paper-md-review 只审查这份MD，输出问题，不修改。
$paper-template-compose 用已登记组件规划一个衍生模板，先给组合方案。
$paper-export 使用已确认的MD、模板和字体，生成首版Word。
$paper-visual-review 检查这份Word，给页面预览和复检报告，先不要修复。
$paper-revise 修复报告中我批准的F003、F007，保留其他内容。
```

技能名称是开发规划名称，安装完成前不能告诉用户这些入口已经可用。

### 5.2 路由规则

优先顺序为用户指定单技能、明确任务动作、完整工作目标。用户说“只检查”时只进入检查；“技能怎么使用”进入说明；“比赛成果转论文”进入总技能。

单技能只核对自身所需输入与有效授权，不强制用户重复全流程。例如作者提供的已有 Word 可直接视觉复检；纯格式导出不要求重做数学证明，但必须标识“未重新验证科学结论”，并核对当前内容确认和生成授权。

完整新论文路线需要模型与主张证据。缺少实验数据时可以整理引言、模型和算法的草稿，不能填入或批准虚构结果，也不能据此宣称完整论文可交付。

## 6. 模板组件系统

### 6.1 三类组件

| 类型 | 职责 | 典型组件 |
|---|---|---|
| 内容结构组件 | 章节目的、顺序、必需内容和审查提示 | 问题重述、假设与符号、模型、求解、实验、讨论 |
| 物理排版组件 | 页面、区域、段落样式和对象布局 | 页面、前置区域、正文区域、篇末摘要、公式编号、题注 |
| 检查组件 | 可执行契约与视觉清单 | 缺摘要、断引用、错误题注位置、公式裁切、正文越栏 |

同一个内容组件能进入不同排版区域。例如模型建立章节可用于国赛单栏正文，也可用于双栏期刊正文。

### 6.2 共用组件目录

| 组件组 | 首版组件 | 主要参数 |
|---|---|---|
| 页面与区域 | `page.base`、`region.front`、`region.body`、`region.end` | 纸张、边距、栏数、合法分节、分页起点 |
| 前置信息 | `title.bilingual`、`authors.affiliations`、`abstract.single`、`abstract.bilingual`、`keywords`、`summary-sheet` | 语言、字段角色、顺序、摘要位置、匿名要求 |
| 正文结构 | `section.introduction`、`section.problem`、`section.assumptions`、`section.notation`、`section.model`、`section.algorithm`、`section.validation`、`section.discussion`、`section.conclusion` | 必填/可选、标题措辞、层级、应表达的内容 |
| 数学对象 | `math.inline`、`math.display`、`math.multiline`、`math.number`、`theorem.proof` | 稳定 ID、显示编号、对齐锚点、可逆换行、区域宽度 |
| 图表 | `figure.inline`、`table.three-line`、`caption`、`cross-reference` | 题注位置、双语、顺序、宽度预算、行间分页 |
| 文献与附录 | `bibliography`、`appendix`、`supporting-files`、`ai-use-statement` | CSL、附录编号、支持材料、对应目标的声明要求 |
| 导航 | `toc`、`page-number`、`header-footer` | 是否允许目录、页码起点、队号或匿名信息 |
| 检查 | `check.structure`、`check.evidence`、`check.content`、`check.math`、`check.geometry`、`check.visual` | 严重等级、阈值、对象定位、人工审阅要求 |

组件不能假设每份论文都需要作者信息、目录、双语摘要、定理或 AI 声明。模板根据实际目标选择。

### 6.3 组件契约

每个组件至少登记：`id`、`version`、`kind`、`input_schema`、`requires`、`provides`、`allowed_regions`、`parameters_schema`、`checks`、`source`、`license`。

接口采用少量固定生命周期：`plan`（确定角色与区域）、`render_docx`、`render_latex`、`check`。纯内容组件可只提供 MD 片段和角色说明；不为了形式增加空实现。

组件参数由模板维护文件声明。用户稿件只能提供内容和语义标记，不能提供任意可执行插件路径、样式 XML 或 Python/Lua 代码。

### 6.4 组合策略

```text
已登记组件 + 版本化组合清单
              │
              ▼
JSON Schema校验 + 依赖/重复/冲突检查
              │
              ▼
唯一的样式集 + 页面区域计划 + 对象编号计划
              │
              ▼
Actions构建模板候选 → 示例渲染与自动检查 → 视觉审阅
              │
              ▼
登记固定母版及指纹 → 稿件生成只读取该资产
```

组合器统一管理页面、分节、全局样式、页眉页脚和编号。组件提供角色与局部行为，不能各自插入任意 `sectPr` 或定义同名全局样式。

新模板尽量只增加组合清单、MD 结构提示与目标来源。若要求现有组件不能表达，例如特殊封面、复杂作者脚注或公式编号方式，新增一个可测试组件，再供其他模板复用。

### 6.5 冻结母版与字体变体

模板开发阶段允许代码生成和维护母版；单次稿件填充阶段只选择已登记资产。

已登记母版按模板版本、区域计划、字体方案和合法变体确定指纹。首次使用自定义字体时，先通过模板构建任务建立新变体，经检查和确认后登记，再执行稿件导出；不在填充时临时改字。

骨架资产包括段落样式、字符样式、表格规则、区域锚点、元数据变量和固定分节。docxtpl 只替换许可变量；正文内容以受限对象填入固定区域。

### 6.6 兼容检查

- 同一个 `title_zh`、`abstract_en` 或正文角色不能被两个组件重复占用。
- 所有使用的全局样式有唯一登记定义；不能靠输入文档补缺样式。
- 节序列来自区域计划；正文不因图片、表格或公式新增分节。
- 匿名模板禁止作者单位组件输出身份；需要目录与禁止目录的规则不能同时生效。
- 页面宽度与栏数必须能提供正的对象宽度预算；公式编号区计入预算。
- 显示编号只有一个生成器；正文引用、图表题注和公式编号使用同一个映射。
- 字体在实际 runner 存在且含所需字形；缺字体不能自动换为备用字体。
- 官方要求与用户覆盖项必须有冲突处理记录。

### 7.1 每类模板的完整文件组


9 类模板不是 9 个新的技能入口。模板是总技能与专业技能共同读取的数据资产。

## 8. MD 论文与共同内容表示

### 8.1 输入选择

首次写作按以下顺序处理：读取用户已经提供的模板或参考材料；询问尚未提供但影响结构的资料；若没有指定模板，推荐已登记的适用模板；提交标题、摘要与章节结构方案供用户确认。

已确认模板保持稳定。用户临时要求新章节时，先说明与模板结构的关系；内容型扩展可按允许的扩展点增加，版式型扩展进入模板维护。

### 8.2 内容源

唯一论文内容源为 `manuscript.md`，含必要结构化元数据、Markdown 正文、LaTeX 数学及稳定对象 ID。图片和文献库是其旁置资源。旧版 `metadata.json` 作为兼容输入，在 Actions 中合并并检测重复或矛盾，逐步迁移为 MD 元数据或由其导出的结构记录。

引擎不得另行维护 Word 文稿正文。实验代码、数据和模型稿继续作为证据材料；审查标记保存在旁置登记，不显示在正式论文正文。

### 8.3 共同表示

Pandoc AST 作为内容解析权威；旁置 `document-map.json` 保存章节角色、区域、源位置和对象 ID。不得给 Pandoc AST 自行增加不兼容字段再直接交给官方 writer。

共同表示覆盖正文、前置信息、摘要、关键词、题注、脚注和附录。摘要中存在行内数学时同样以 AST 保留，不能降为简单字符串而丢失公式。

稳定 ID 与显示序号分离：`eq:M1`、`fig:architecture`、`tab:parameters`、`sec:model`。模型稿保留 M1—M30；论文稿按模板连续编号，映射保留原模型 ID。新增对象插入后重新生成显示编号，不改变稳定 ID。

### 8.4 语义与物理格式分离

正文允许加粗、斜体、上下标、章节角色、对象 ID 和语义性脚注。模板控制字体、字号、页面、分节、栏数、缩进和物理尺寸。

Markdown 图片尺寸等物理属性不能控制成品；能明确忽略的属性记录在转换报告中。原始 OOXML、任意 HTML 排版、LaTeX 页面控制、外部过滤器命令、未知可执行资源明确拒绝并定位。

如果已公开论文含混合 LaTeX 语义命令，只使用现有受限语义导入器支持的子集。用户原稿和归一化记录分别保存，不能以为了过检查为由改写源公式。

### 8.5 MD 审查通过条件

- 题目、摘要、关键词和核心结论一致。
- 章节顺序与章节角色正确，标题内容对应，无明显逻辑断裂。
- 模型定义、符号、单位、假设、约束和目标一致。
- 结果主张可关联实际数据、分析或推导，缺证据项已解决。
- 全部公式经过相应数学审查，且转换能力检查通过；两者分开记录。
- 每个图表有名称、资源、编号和有效正文引用；表格数据完整。
- 文献身份核实，引用完整，无虚构 DOI、卷期、作者或页码。
- 必需的声明、匿名要求和支持材料齐全。
- 用户确认的是当前文件、资源和模板选择对应的同一快照。

## 9. Word、LaTeX 与公式实现

### 9.1 Word 正式链路

```text
已批准内容快照
  → Pandoc AST与共同对象映射
  → Pandoc原生DOCX内容/OMML
  → 净化输入直接格式和分节
  → 读取登记母版并核对指纹
  → docxtpl填充许可的纯文本变量
  → python-docx/lxml填充角色化正文与数学对象
  → OOXML契约检查
  → LibreOffice校样与页面检查
```

docxtpl 负责题目、作者、单位、队号及固定标签等变量；数学或复杂摘要经 AST 对象填入区域。不得使用可传入任意 XML 或字体的内容值替代受限对象。

需要 `autoescape=True`、严格未定义变量处理、控制字符校验和模板变量白名单。内容中出现 `<`、`>`、`&` 应安全保留，不能因 XML 转义丢失。母版变量不能被 Word 切分到未经支持的多个 run；构建时检查。

填充不能导入输入 DOCX 的主题、页眉页脚、样式和分节；图片、超链接等内容资源按白名单导入。禁止从用户上传任意 DOCX 直接作为正式母版，必须先经过模板审查、登记和云端验收。

### 9.2 分节与页面

从 `layout_plan` 生成合法区域及节序列，每个对象获得所属区域和宽度预算。单栏与双栏模板共用同一个生成器；检查也读取区域计划，不再写死期望 `[1,2]`。

稿件填充不新增正文分节。前置信息、摘要专页、目录和篇末摘要的分页来自模板计划。图片和公式不能触发自动退出双栏。

区域切换应验证真实页面，避免连续分节的栏平衡造成大留白。章节标题不得固定每节换页；不将全部段落设为 keep-with-next。

### 9.3 公式与编号

保留原生 OMML，默认复用既有 Pandoc 转换、可逆换行记录和数学树回读。不转换为截图，不通过缩小字体或改变数学内容解决宽度。

首版公式组件继续采用独立标记的无边框布局表，把公式区域与编号区域分开。该表不能被当成数据表加三线，也不能加入表格序号。

编号对齐规则必须显式定义：单行公式采用约定基线；分段或多行公式采用约定的整体中心或末行锚点。数据结构记录 `alignment_anchor`，不以“旁边有文本”冒充对齐通过。使用单元格垂直对齐、段落间距和数学行盒设置实现，并由校样测量和人工复检确认。

公式宽度预算扣除编号区和间距。长公式先保留作者已确认多行结构；新增排版换行只在受支持数学树边界进行，记录可逆变化与对应 ID。普通矩阵不改变列数；运算顺序、括号作用域、上下标和条件归属不得改变。

分母、根号、求和上下限等高度需要数学对象排版，不能使用可能裁切公式的固定小行高。单个不可拆对象仍超出区域时输出 `OBJECT_DOES_NOT_FIT`，保留诊断版，进入经用户批准的处理，不自动跨栏。

### 9.4 图表

按本项目用户选择，图题在上、表题在下；固定生成器按模板契约执行。模板保留官方默认与用户审阅变体的来源差异。

图和表各自按出现顺序编号，不能混用一个序列。题注含实际名称，不能只有“图 1”或“表 1”。题注与对象一起布局；图上题与图片 keep-with-next，表下题需要在表末行与题注间控制分页，不能简单对题注设置向后关联。

表格固定在区域宽度内，数据保持可编辑；三线表不出现意外竖线。长表允许按模板在行间分页或换栏，表头重复与续表题是否允许由契约确定。跨页重复表头不能被内容审计误计为新数据。

图片按比例限制在区域宽度内，不拉伸、不裁切。需要新增清晰图件时回到内容/图件制作授权，不用排版器伪造实验图。

### 9.5 LaTeX

LaTeX 使用同一 AST、区域计划、内容角色和显示编号。前置信息、正文及附录不各自维护不同正文。单栏/双栏来自模板计划；禁止因图表或公式临时退出正文区域。

模板参数通过登记的渲染适配器输出。保留直接源公式及允许的排版转换映射。两种输出允许分页不同，不要求像素级相同，但正文、数字、数学结构、表格、引用和图片身份一致。

### 9.6 字体

用户选择至少覆盖中文正文和英文字体；数学字体单独记录并检查与两套输出的兼容性。提供以下选择类型，实际可用项以云端字体清单为准：

| 选项 | 中文 | 英文 | 数学 | 处理方式 |
|---|---|---|---|---|
| 开源推荐 | 思源宋体 / Noto Serif CJK SC | Liberation Serif | Latin Modern Math | 可作为本项目云端起点，经用户确认后冻结 |
| 常见论文组合 | 宋体 | Times New Roman | Cambria Math | 用户或运行环境需具备可用字体与相应使用权；缺少时报告，不自动替换 |
| 自定义 | 用户指定 | 用户指定 | 按支持情况选择 | 先核对字体来源、可用字形和云端运行能力，再构建变体 |

字体替代必须由用户批准，且报告指出与参考论文的差异。跨 Word 与 XeLaTeX 字体不完全相同时，先说明并确认；不能将不同字体声称为精确复现。

## 10. 项目档案、证据与要求冲突

### 10.1 项目档案

项目状态记录需求、研究类型、语言、目标及年份、输入材料、选择模板、字体方案、已完成阶段、审批、云端运行和待处理问题。状态保存在项目范围，不改用户全局配置。

`project.md` 用于用户阅读；`project.json` 和事件记录用于云端契约核对。手工编辑状态不构成审批证据，也不能覆盖已有云端结果。

### 10.2 规则来源档案

每条规则登记来源类型、URL 或文件、版本/年份、页码或章节、观察结果、适用对象、置信度、是否强制、与其他来源差异和采用理由。

来源类型为 `user_choice`、`published_reference`、`official_requirement`、`engineering_default`、`recommended_structure`。工程参数不得伪装成参考实测值；推荐章节不得伪装成比赛官方固定章节。

扫描 PDF 或低质量抽取标记为待核实；文字抽取结果不能独立证明栏数、字体和题注位置。需要页面证据时通过 Actions 生成预览并查看。

### 10.3 冲突记录

冲突至少包含 `property`、冲突值、来源、影响、推荐处理、用户决策、适用版本。按冲突性质给出可理解的选择，例如官方提交版和个人审阅版；不能对硬性要求违规的输出标为“官方合规”。

对于本次图表位置要求，原参考与官方可能采用图下题、表上题，必须在对应模板中记录这一差异。开发文档记录处理机制，不擅自改变已确认偏好。

### 10.4 事实与模型证据

复用 K-Dense 的证据登记与一致性检查思路，形成主张、来源、方法、结果的明确关系。公开文献元数据核实与支持具体结论的全文证据核实分开；存在 DOI 不等于结论受支持。

主张可由理论推导、数据、实验输出或可靠文献支持。解释性判断保留其证据和不确定性。审查项目只要求对科学主张与关键数字登记，不把作者姓名、年份、编号、维度和页码一概当成实验结果。

模型验证至少区分定义与边界审查、约束一致性、必要推导/证明、算法实现对应、测试实例、结果复现和泛化证据。不会把格式验收、一次求解成功或文字审查宣称为数学正确性证明。

实验执行如果属于用户授权范围，提交代码、数据和运行参数到独立 Actions 作业；没有执行的实验保留未验证状态，不生成通过报告。

## 11. 流程状态与审批

### 11.1 主流程

```text
intake
  → plan_confirmed
  → references_ready
  → model_reviewed（适用时）
  → model_confirmed（新模型论文必须具备对应验证）
  → md_draft
  → md_reviewed
  → md_confirmed
  → presentation_confirmed（字体、模板变体、冲突已处理）
  → export_authorized
  → cloud_build
  → visual_review_reported
  → awaiting_user_decision
       ├─ approve_delivery → delivered
       └─ approve_findings → revision_authorized
                             → revised
                             → cloud_build
                             → visual_review_reported
                             → awaiting_user_decision
```

单技能使用从有效输入对应状态进入，不创建假的已完成阶段。实际只生成 Word 的任务可以不构建 LaTeX，但必须报告覆盖范围；完整套件发布仍需要两种输出验收。

流程通过 transitions 的显式条件控制。状态机只是通用运行机制，审批真实性与材料指纹需要本项目业务适配；不会因为引入状态机库就自动拥有可信审批。

### 11.2 审批类型

| 类型 | 用户批准的具体对象 | 不能替代的审批 |
|---|---|---|
| 工作方案确认 | 本次范围、模板建议、交付物和步骤 | 不能替代模型正确性、最终内容或导出授权 |
| 模型确认 | 当前模型和对应验证结论 | 不能替代后续论文内容确认 |
| MD 内容确认 | 当前题目、正文、公式、图表、文献快照 | 不能自动表示同意生成 Word |
| 表现方案确认 | 字体、模板版本、变体、冲突处理 | 不能改变已批准科学内容 |
| 导出授权 | 用当前内容和模板生成指定产物 | 不能替代修复授权或投稿授权 |
| 修复授权 | 当前报告的问题项与修改范围 | 不能扩大为任意重写或无限迭代 |
| 交付确认 | 当前产物与复检报告 | 不等于授权投稿、发布或发给他人 |

用户在一句话中明确批准多个事项时可以建立多个对应记录，不能为了流程形式重复提问。方案获批后允许在已授权范围内继续开发，不将每个内部步骤都变成用户审批。

### 11.3 审批绑定

审批绑定内容快照、模板身份、字体方案、资源指纹、报告或问题清单，以及原始用户意思的引用和来源。云端记录实际输入提交、引擎提交与文件指纹。

AI 只能如实记录用户批准，不能自行填写一个布尔值就将其视为独立的人类身份认证。首版以对话中的明确指令和可追踪记录为授权依据，Actions 校验范围与文件绑定；需要更强的人类身份核验时，可扩展为用户在 GitHub 发起指定工作流等操作，不在首版引入付费审批平台。

### 11.4 失效规则

- MD 正文、公式、图表名称、数据或文献内容变化：使对应内容确认和后续导出授权失效。
- 图片实际内容、实验数据、模型代码或结果变化：使受影响证据和内容确认失效。
- 只改变字体或母版：内容确认保留，表现确认与对应导出授权需重新绑定。
- 只改变检查器版本：不能覆盖旧报告；新检查生成新的结果与指纹。
- 使用已经批准的修复范围修改物理排版：保留内容确认，重新验收实际输出。
- 对科学内容的修复：回到 MD、证据和内容确认；先批准改动方向，再确认修订结果。

通过 Git 保存不可变快照，利用既有指纹功能检查产物。`difflib` 和 Git diff 提供文本差异；对象级变化通过稳定 ID 对照。不自行造版本控制系统。

## 12. 数据契约与接口设计

本节字段是开发契约，示例中的版本、指纹和运行号是占位值，不代表已经形成对应资产或获得审批。正式接口使用 JSON Schema Draft 2020-12；跨文件指纹、状态和对象关联由业务校验器补充，不能只靠字段类型检查。

### 12.1 核心记录

| 记录 | 必需字段 | 权威来源 |
|---|---|---|
| 技能目录 | `schema_version`、`suite_version`、`skills`；每个技能含名称、说明、输入、输出、能力和独立调用示例 | 套件维护文件 |
| 模板身份 | `template_id`、`template_version`、`variant_id`、`font_profile_id`、`manifest_sha256` | 已登记模板清单 |
| 组件身份 | `component_id`、`component_version`、类型、依赖、接口、参数契约、检查和来源 | 组件注册表 |
| 文稿快照 | MD、图片、文献和旁置文件的相对路径、SHA-256、资源类型 | 实际输入提交 |
| 对象映射 | 稳定 ID、对象类型、源位置、章节角色、显示序号、引用、所属区域 | 云端 AST 解析 |
| 证据登记 | 主张 ID、证据 ID、主张类型、出处/执行产物、范围、核查状态、不确定性 | 实际材料和审查记录 |
| 审批事件 | 类型、批准对象、范围、原始用户指令来源、关联指纹、时间、被替代事件 | 用户明确意思及可追踪记录 |
| 构建清单 | 引擎提交、输入提交、依赖清单、模板指纹、所有产物指纹、运行身份 | 实际 Actions 运行 |
| 复检问题 | 问题 ID、检查项、对象 ID、页面与区域、等级、证据、建议、状态 | 自动检查或逐页视觉复检 |

所有版本化记录包含 `schema_version`。初版不会要求稿件作者手工填写这些技术字段；技能维护记录，用户查看自然语言说明和报告。

### 12.2 模板组合清单

以下用于说明组件接口，不是任意一个期刊的最终章节或测量规则：

```yaml
schema_version: 1
template_id: reference-journal-v1
template_version: "next-candidate"
variant_id: personal-front-abstract
source_rules: rules.json
font_profile_id: open-serif-confirmed
components:
  - id: page.base
    version: "1"
    parameters_ref: parameters/page.json
  - id: region.front
    version: "1"
    parameters: {columns: 1}
  - id: region.body
    version: "1"
    parameters: {columns: 2, allow_spanning_objects: false}
  - id: title.bilingual
    version: "1"
  - id: abstract.bilingual
    version: "1"
  - id: math.number
    version: "1"
    parameters: {numbering: preserve_model_ids, multiline_anchor: center}
  - id: caption
    version: "1"
    parameters: {figure_position: above, table_position: below}
checks:
  - check.content
  - check.math
  - check.geometry
  - check.visual
compliance:
  official_submission: false
  unresolved_conflicts: []
```

组件参数只能在模板维护流程修改。生成请求不接受这份清单作为临时覆盖，而是引用其验收后形成的身份与指纹。既有 2.2 cm 等工程值放入页面参数文件并标明来源，不能填成官方实测数据。

### 12.3 导出任务清单

正式导出清单采用“内容文件白名单 + 登记模板身份 + 有效授权”，不上传整个工作区：

```json
{
  "schema_version": 2,
  "task_id": "model-first-export",
  "operation": "export",
  "engine_commit": "<approved-engine-commit>",
  "input_commit": "<immutable-input-commit>",
  "template": {
    "id": "reference-journal-v1",
    "version": "<registered-version>",
    "variant": "personal-front-abstract",
    "font_profile": "<confirmed-font-profile>",
    "manifest_sha256": "<manifest-sha256>"
  },
  "manuscript": "manuscript.md",
  "files": [
    {"path": "manuscript.md", "sha256": "<sha256>", "role": "manuscript"},
    {"path": "images/model.png", "sha256": "<sha256>", "role": "image"},
    {"path": "references.bib", "sha256": "<sha256>", "role": "bibliography"}
  ],
  "approvals": {
    "md_content": "approval-md-001",
    "presentation": "approval-presentation-001",
    "export": "approval-export-001"
  },
  "outputs": ["docx", "latex", "docx-proof-pdf", "latex-pdf", "previews"]
}
```

`task_id`、路径和枚举受限；路径不得越出任务根目录。输入清单的未知字段报错，特别是 `profile`、`font_size`、`columns`、`margins`、`section`、`template_path` 和任意过滤器命令。这里的字体方案是已经登记的身份，不是随稿件修改字体的参数。

工作流的 `input_commit` 是实际检出权威值。清单中如同时记录提交，必须相同；不能由清单宣称使用一个提交，却实际读取另一个分支的内容。

模板构建为独立维护任务，输入组合清单和维护源码，不能冒用普通导出操作绕过模板登记。

### 12.4 审批与修复记录

审批事件必须表达批准的对象，不能只有 `approved: true`。必要字段包括：

```text
event_id、event_type、project_id、actor_type
user_instruction、instruction_source、recorded_at
content_snapshot_sha256、template_manifest_sha256、font_profile_sha256
approved_outputs、approved_finding_ids、allowed_change_types
supersedes、validity_status、invalidated_by
```

不适用的字段可以省略，但某类事件的必需字段由 Schema 指定。修复授权必须有问题 ID 或明确范围，以及对应报告和产物指纹。报告更新不能使旧授权自动扩张到新发现的问题。

人工身份不能通过 `actor_type` 字段自行证明。首版记录对话授权来源与适用范围，不把记录文件称为数字签名或不可伪造凭证。

### 12.5 复检报告契约

报告顶层分别记录：

```text
build_status: succeeded | failed | not_run
automatic_status: passed | failed | incomplete | not_run
visual_status: completed | incomplete | not_run
visual_result: passed | issues_found | not_assessed
delivery_status: awaiting_user | approved | rejected | diagnostic_only
```

每个问题包含 `finding_id`、`check_id`、`origin`、`severity`、`object_id`、`output_kind`、`page`、`bbox`、`preview_path`、描述、影响、处理建议和状态。不能精确自动定位时，标记位置是人工定位或未知，不生成假的坐标。

自动验收失败时仍生成报告与可用诊断附件。视觉审阅可以完成并发现问题，不能把“已看完”转换成“通过”。

### 12.6 云端能力与本地传输接口

本地保持现有三个入口：

```text
paper.py submit  提交清单指定文件并发起工作流
paper.py status  查询指定任务或运行
paper.py fetch   下载指定运行的产物
```

参数兼容性以现有入口为迁移基础，完整 CLI 说明在实现时更新。接口可以读取清单、复制文件和调用 GitHub，但不能在本地运行模板检查器、Pandoc、公式转换、编译器或渲染器。

云端能力划分为 `reference`、`model-review`、`md-review`、`template-build`、`export`、`visual-receipt` 和 `package`。写作及视觉看图由当前 Codex 执行；Actions 不调用额外 LLM。云端命令在进入业务函数、创建输出或启动子进程前检查 Actions 运行条件。

缺少运行环境时拒绝执行。这是防止误调用的保护，不宣称仅靠环境变量能认证真正的 GitHub runner。

### 12.7 失败分类

| 错误码 | 触发条件 | 必须报告 |
|---|---|---|
| `ACTIONS_REQUIRED` | 本地误调用执行性入口 | 被阻止操作及未执行状态 |
| `UNKNOWN_TEMPLATE` / `TEMPLATE_NOT_READY` | 模板不存在、版本错误或输出能力未验收 | 模板身份、缺失能力 |
| `TEMPLATE_INTEGRITY_MISMATCH` | 母版或配置与登记指纹不同 | 具体资产与实际/预期指纹 |
| `FORBIDDEN_LAYOUT_OVERRIDE` | 内容或请求注入物理版式 | 字段、文件、源位置 |
| `RULE_CONFLICT_UNRESOLVED` | 必要规则冲突未决定 | 冲突项、来源与影响 |
| `APPROVAL_MISSING` / `APPROVAL_STALE` | 授权缺失或与输入不匹配 | 所需授权与变更对象 |
| `MODEL_EVIDENCE_INCOMPLETE` | 新模型论文缺必要验证 | 未验证主张与所需证据 |
| `FONT_MISSING` / `GLYPH_MISSING` | 字体或实际所需字形缺失 | 字体身份与字符位置 |
| `RESOURCE_MISSING` / `REFERENCE_BROKEN` | 图片、文献或交叉引用无法解析 | 稳定 ID 与源位置 |
| `DUPLICATE_ID` / `NUMBERING_CONFLICT` | ID 或显示编号冲突 | 全部冲突对象 |
| `MATH_CONVERSION_FAILED` | 公式不能安全转换或回读不一致 | 公式 ID、原式、阶段与诊断 |
| `OBJECT_DOES_NOT_FIT` | 公式、图片或表格不能按契约容纳 | 对象、区域预算及超出证据 |
| `CONTENT_CHANGED` | 回读正文、数据或结构变化 | 对象级差异，不能仅给一个失败布尔值 |
| `VISUAL_REVIEW_INCOMPLETE` | 未审阅全部应查页面或缺关联证据 | 缺少页面和检查项 |
| `REVISION_SCOPE_EXCEEDED` | 修订超出批准问题项和修改类型 | 未获授权的差异 |

## 14. GitHub Actions 执行与可复现链路

### 14.1 工作流划分

| 工作流 | 触发方式 | 职责 | 输出 |
|---|---|---|---|
| `skill-ci.yml` | push、PR、手动 | 技能/契约检查、单元测试、回归测试、选定双输出集成、安装包检查 | 测试报告、诊断产物、候选包 |
| `document-task.yml` | `workflow_dispatch` | 指定输入提交的参考分析、审查、导出或视觉收据验证 | 用户任务产物与运行清单 |
| `template-ci.yml` | 模板或组件变更、手动 | 9类模板及变体的组合、母版构建、字体检查和页面回归 | 母版候选、规则报告、模板预览 |
| `build-core.yml` | `workflow_call` | 共用依赖安装、构建、回读、渲染和报告步骤 | 被调用工作流的产物 |
| `word-comparison.yml` | 既有独立实验入口 | 保留历史技术对比；不触发正式默认生成器 | 隔离的对比报告 |

复用 GitHub 原生 [reusable workflows](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)，不自行写任务调度平台。不是每次说明技能调用都启动工作流；只有需要执行性处理时提交任务。

### 14.2 输入与引擎隔离

手动工作流定义必须位于默认分支。运行同时记录代码的 `engine_commit` 与材料的 `input_commit`，分别检出到不同目录。执行源码只来自指定、已登记的引擎提交；稿件目录仅作为数据读取。

导出操作不能执行稿件内的 shell、Python、Lua 过滤器或自定义 TeX 命令。研究模型代码的验证是单独、已授权的实验任务，不与文档填充混为一体。

使用既有 GitHub 授权和最小必要工作流权限。普通构建只读仓库，模板发布需要写入资产时使用独立维护步骤；不默认授予所有任务写权限。

### 14.3 标准执行顺序

```text
1. 检出引擎和清单指定输入
2. 校验运行环境、任务契约、身份、授权和文件指纹
3. 安装锁定的工具与字体；生成实际依赖清单
4. 解析唯一内容源与对象映射；检查结构、资源和证据边界
5. 核对已登记模板；分别构建DOCX和LaTeX
6. 回读并比对正文、数学、数字、图表、引用
7. LibreOffice生成DOCX兼容PDF；XeLaTeX生成LaTeX PDF
8. Poppler输出逐页PNG；生成可测量的页面检查结果
9. 写入独立状态、错误清单、指纹和预览索引
10. 无论成功或失败，上传已有诊断和报告，默认保留30天
11. 当前Codex下载/查看预览，按清单逐页视觉审阅
12. 提交绑定当前运行与产物的视觉收据，Actions核验关联
13. 给用户首版产物、附件和报告，等待交付或修复决定
```

第 11 步不等于本地渲染：本地只查看 Actions 产出的图片。视觉收据验证检查页码覆盖、检查项和指纹，不能替代真正的看图，也不能证明审阅者一定认真检查。

### 14.4 依赖锁定与现有版本

迁移从现有工程版本起步，不为引入组件系统同时升级全部转换器：

| 工具 | 当前迁移起点 | 处理原则 |
|---|---|---|
| Python | 3.12.8 | 保留；新增依赖先在Actions核对兼容性 |
| python-docx | 1.2.0 | 保留，避免同时更换底层文档处理 |
| lxml | 6.0.2 | 保留，配合OOXML契约 |
| pytest | 8.4.2 | 只在Actions执行 |
| Pandoc | 3.12.1 | 使用现有二进制SHA-256；转换变化另做回归 |
| LibreOffice | 26.8.1 | 保留当前固定安装包和指纹；清楚标记其渲染来源 |
| Jinja2 / docxtpl / jsonschema / transitions | 本轮未新增安装 | 实施时选择兼容的发布版本并固定，不能以调查的Git HEAD冒充依赖锁定 |
| XeLaTeX / Poppler / 字体 | 按现有安装流程迁移 | 补充实际包版本、字体文件指纹与runner镜像信息 |

现有 Pandoc 包 SHA-256：`b4217ac7c54067c442f9d4cd38bcd0c184a43f3e7053431a12263a6f92a33ba2`。现有 LibreOffice 包 SHA-256：`30903df3b9f61360d9660cd707de48cd2831469114492a5008ed58a0ac77d044`。这些是已有配置值，本轮没有下载或运行验证。

所有第三方 Actions 固定到提交 SHA。Python 依赖采用固定版本和可核验下载散列；记录实际 runner 镜像、TeX、字体及系统包版本。只写 `ubuntu-24.04` 或 apt 包名不能保证长期完全相同，必须在报告中说明可复现边界，必要时使用版本化构建镜像。

### 14.5 并行、缓存与产物

契约和内容解析通过后，DOCX 与 LaTeX 构建可以作为独立作业并行。不得并行改同一文件或用一套输出的修复结果偷偷改变另一套输入。最终合并报告核对共同输入和对象映射。

缓存键包含锁定依赖、转换器和字体指纹，不能复用未知版本的母版。用户任务输入与诊断不进入公共依赖缓存。

每次完整导出至少包含：

```text

manuscript.docx           可编辑Word
latex-project/           完整源、图片、文献、编译说明
```

### 14.6 发布门槛

技能或模板正式发布必须同时满足构建成功、自动验收通过、视觉审阅完整且结果通过，以及对应发布范围确认。用户论文首次诊断版不需要伪装为满足这些门槛，发现问题照实交付并保留。

不能以 Actions 绿色状态替代用户的内容确认、修复批准或最终交付确认；也不能让一份“视觉完成”记录掩盖仍未解决的问题。

### 15.2 公式对齐测量的边界

PDF 文本坐标可定位普通编号，数学字符的基线提取不一定完整。首版先对可测量锚点做明确阈值检查，结合对象边界和页图；无法可靠自动测量的表达式必须进入视觉必查，不宣称全自动证明对齐正确。

阈值由固定字号和云端回归样例标定并作为模板检查参数保存。不得在看到某篇失败后临时调大阈值，以此把结果改成通过。编号附近存在文字、公式数量相等、`w:cols=2` 都不能单独作为页面合格依据。

### 15.3 问题等级

`blocker`：科学内容变化、公式丢失或变义、表格数据错误、缺关键资源、模板完整性或审批失效。不能作为正式完成版本。

`major`：越栏、裁切、编号明显错位、题注错误、意外空白页或缺字。保留首版并请求对应修复决定，不宣布排版验收通过。

`minor`：不影响内容但需改善的间距、对齐细节或非强制风格差异。仍向用户披露，是否接受由用户决定；模板发布的必需检查项不能用“minor”绕过。

### 15.4 给用户的固定报告结构

报告依次说明当前稿件与版本、三项构建/自动/视觉状态、已检查页数与渲染来源、符合项、问题清单、逐项证据、建议修复范围、已知限制和需要用户决定的事项。

每个问题用“页码—对象—看到的现象—影响—建议”表达，附对应云端页面或裁切附件。表格记录问题 ID，便于用户说“批准修复 V11 和 V16 对应问题”。

第一版明确标为第一版；用户只要求查看 Word 时先提供可下载 Word 和关键问题，不让用户翻阅大量技术日志才能找到文件。

### 15.5 修复循环

复检完先提交报告，收到用户批准后按指定范围修改。修复时不改变无关内容或用源文稿改动掩盖转换失败。重新构建、检查和逐页审阅，保留上一版和差异，再提交当前结果。

已经批准一组问题的完整修复时，可以在该范围内持续排查代码并重跑 Actions，无需对每次内部调试重复询问。新增问题或扩大科学内容修改时才需要新的范围确认。

每类模板都需要一个最小完整样例和一个包含数学、图、表、引文的组合样例。共同公式/表格组件的复杂场景可以共享夹具，但每类模板必须验证实际栏宽、字体与分节契约，不能只测试共同代码。

没有可靠官方 Word 母版但有官方 LaTeX 规范时，根据已确认规则建立自己的 Word 变体，并注明其来源与适配身份，不能标为官方原版 Word 模板。

### 16.4 首次使用复刻测试

完成内核后安排一次正常用户流程测试，目标是观察用户实际得到的第一版，不是经过人工特调后的演示版：

1. 选取一篇许可允许使用、可取得 Markdown/数学源且含复杂公式与图片的公开研究稿件，记录原始来源、许可、版本与文件指纹。此前删除的私人/测试材料不自动恢复。
2. 先使用说明技能与总技能确定目标，再按参考研究、MD审查、字体确认和生成授权推进。已发表论文的纯复刻不重新宣称验证其全部数学证明。
3. 使用已经验收的登记模板，不修改源文稿使其更容易通过，不根据这篇稿件临时修改母版，不预先为它单独排版。
4. 第一轮通过标准 `document-task.yml` 生成并保留产物，无论自动结果如何，都给出真实第一版Word、云端校样和报告。
5. 按清单逐页检查，用户批准后才能开始对应修复。之后的版本分别编号，不称为第一版。

选材标准是具有求和/分式、分段或矩阵、多行表达式、上下标、至少一个长公式，以及图、表、正文引用。可设置至少 20 条显示公式作为复杂样例工程标准；这个数量不是论文质量标准。未找到许可合适的论文时明确报告，不把自行合成材料冒充已发表论文。

同时保留一个合成压力样例覆盖极端布局，以及在用户授权清单范围内使用现有 M1—M30 模型作私人回归。这三类用途分开：真实首次体验、极端能力边界、当前模型保留。

## 17. 内核实现约定与算法边界

### 17.1 注册、计划与输出的内部接口

内部接口以现有 Python 模块为基础，采用明确的数据结构，不增设网络服务。规划接口如下：

```text
resolve_template(identity) -> RegisteredTemplate
validate_composition(manifest, registry) -> CompositionReport
build_layout_plan(template) -> LayoutPlan
load_approval_context(project, snapshot) -> ApprovalContext
check_transition(current_state, event, context) -> Decision
parse_manuscript(source, resources) -> PandocAST + DocumentMap
resolve_objects(ast, map, numbering_plan) -> ResolvedContent
render_docx(content, template, output) -> BuildResult
render_latex(content, template, output) -> BuildResult
check_roundtrip(source_content, outputs) -> ContentReport
check_pages(rendered_pages, layout_plan) -> GeometryReport
validate_visual_receipt(receipt, build_manifest) -> ReviewBindingReport
check_revision_scope(before, after, authorization) -> ChangeReport
```

上述为目标职责，不要求照名称重写全部函数。`RegisteredTemplate` 只读；渲染函数不能改写注册目录。`BuildResult` 返回实际产物、状态和错误，不把失败转换为无提示的空文档。

### 17.2 区域宽度与几何预算

区域计划记录纸张宽高、边距、栏数、栏距、页眉页脚空间和合法分页方式。对象预算使用对应区域的有效宽度：

```text
可用横宽 = 纸张宽度 - 左页边距 - 右页边距 - 其他登记占用
单栏宽度 = (可用横宽 - (栏数 - 1) × 栏距) / 栏数
公式内容宽度 = 单栏宽度 - 编号区域 - 编号间距 - 容器内边距
```

统一单位转换到 OOXML 的 twip、图片的 EMU 或 LaTeX 长度，沿用现有单位工具。不能继续在函数中写死 A4 宽度和除以 2。输出测量还需要核对实际页面，几何预算不是最终渲染证明。

### 17.3 内容标识与源位置

保留现有公式 `\tag{M1}` 和显式 `{{eq:M1}}`、`{{fig:...}}`、`{{tab:...}}` 引用的兼容处理；新增 ID 能力通过受支持的 Pandoc 属性或旁置对象映射实现，不另建 Markdown 解析器。文献 citeproc 与对象引用走各自类型，避免将公式 ID 当文献键。

对象身份在编号前固定，显示编号从共同出现序列生成。归一化处理记录合法变化，并对不存在目标、重复身份、空题注、缺正文引用作明确检查。

Pandoc AST 并非天然给每个节点提供准确 Markdown 行号。可用稳定 ID、章节和原文定位的对象先按此定位；只有有可靠映射时才报告精确行列，不凭节点序号虚构源行号。

### 17.4 内容一致性判定

正文使用对象级 token/文字序列比较，允许登记的换行、零宽标记和字段编号变化。不能将所有空格删掉后作为唯一比较，因为英文词、数字和单位可能因此产生假相等。

数字保留符号、小数、指数、单位和所在对象；表格逐格比较，重复表头作为显示副本。图片检查源资源身份与实际嵌入资源映射；如必须发生编码转换，记录其关系，不能要求转换后字节与原 PNG 完全相同。

数学分别核对原 LaTeX、结构化 OMML 回读、允许的排版变化和引用编号。现有数学树工具只在其支持的转换范围判定保留，不将结构一致性测试冒充一般数学等价判定或定理证明。

文献与引用使用稳定键、核实元数据和 citeproc 结果比对。页码、目录字段和自动编号不与源稿固定文字混为一谈。

### 17.5 模板保护与可编辑性

“强制模板”在生成器中通过只读登记资产、输入白名单、角色样式、合法分节和最终契约检查实现。Word 文件仍允许用户正常编辑，不使用密码限制，也不能保证用户手工修改后仍符合模板。

如果用户改过 Word 后要求复检，按新输入处理并指出与原生成指纹的差异；若要保持唯一内容源，经过用户授权再同步必要内容到 MD，不偷偷反向覆盖原稿。

### 17.6 重跑与版本差异

任务身份由输入、引擎、模板、字体和操作共同确定。相同快照重跑只产生新的运行记录；新的内容或模板生成新版本。产物不得覆盖另一运行目录。

代码修复与稿件修复分开登记：代码修复改变引擎提交和生成行为，稿件修复改变源内容。报告说明哪一类变化导致输出不同，避免把排版器问题归咎于用户数学内容。

### 18.1 依赖关系与优先级

P0 → P1 → P2 是内核主链。P3 可在内核开发期间进行资料整理，但 MD 审批仍独立；P4 依赖组件能力与对应来源规则；P5 不得拿未登记模板冒充正常首次体验；P6 最后执行。

先把原参考模板和通用建模模板做可靠，再扩展竞赛及期刊。每类模板增加的是数据和必要适配，不复制一份生成器。对于尚未获得当前年份资产的模板，保持未就绪并继续其独立资料工作，不能阻碍已经有可靠来源的其他模板推进。

### 18.2 原方案的兼容与淘汰

- 旧 `reference-journal-v1` 身份可继续解析，但只能指向对应已验收版本，不能悄悄改变旧指纹。
- 旧 `profile` 输入逐步退出；兼容路径只识别明确映射，遇到试图覆盖物理版式的字段报错。
- 旧纯文件 `metadata.json` 支持一次受控迁移，与MD冲突时报告，不以字段覆盖顺序偷偷选一个。
- 旧自动通栏脚本和 Node 对比实验保持非默认，不借迁移重新启用。
- 原版错误题注规则与新偏好分属模板版本；历史产物不被覆盖，当前任务选择新版。
